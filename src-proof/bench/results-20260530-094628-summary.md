## Findings (for maintainer reply)

### What the proposal can *justify* with these numbers

1. **`TlsSocketBoundSession` (`SSL_set_fd`-direct)** earns its own API. Same C# code
   architecture, the only thing that changes is whether OpenSSL talks to the socket
   directly or whether the app shuttles bytes through a `BIO_pair`:
   - **+148% RPS, +256% RPS/core** (04 vs 05).
   - **−30% mean CPU%** despite handling 2.5× the traffic.
   - This is `TlsSocketBoundSession`'s purpose: it lets `SSL_read`/`SSL_write` do their
     own `recv`/`send`, which removes per-record copies *and* removes the EPOLLOUT
     resume state machine the app would otherwise have to write.

2. **`TlsDetachedSession` (mem-BIO, cross-platform)** earns its own API on a
   *separate* axis — getting out of `SslStream`'s way:
   - **+98% RPS, +105% RPS/core** (02 vs 03).
   - This is the gain consumers get even on Windows (Schannel) and macOS
     (`Network.framework`) where fd-binding doesn't exist. Span-in/span-out TLS
     processing is ~2× the per-core efficiency of `SslStream` because the consumer
     owns buffer management.

3. **Threading model is *not* a proposal axis** (03 vs 05 is +3% RPS / −1% RPS/core).
   Dedicated epoll workers without fd-binding gain nothing. They only become
   meaningful when combined with `SSL_set_fd` — and even then we're not proposing
   threading APIs publicly (Kestrel drives them internally).

### What the proposal can **not** justify with these numbers

4. **`accept4` / `TryAccept`**: at 6 K conn/s the extra `fcntl` syscalls cost
   ~0.1% of a core. The 04→04b delta (−11% RPS / −4% RPS/core) is direction-
   inconsistent and within noise. **Keep `TryAccept` on syscall-ergonomics grounds
   (one syscall vs three, fewer race windows on `FD_CLOEXEC`), not perf.**
   To get a real perf signal here we'd need ~100 K conn/s sustained, which this
   single-box wrk loop cannot generate.

5. **`TCP_DEFER_ACCEPT`**: −9% RPS / −6% RPS/core / −2% CPU vs exp 04. On fast-LAN
   benchmark traffic where the client's ClientHello arrives essentially with the
   SYN-ACK ACK, the kernel-side defer-timer is pure overhead.
   **The honest pitch is DoS / SYN-flood resistance, not throughput** — those
   benefits aren't measurable in a benchmark where every client is well-behaved.
   We can drop this from the perf-API proposal and re-pitch it as a
   socket-hardening primitive if there's appetite for that separately.

### The crisp story for the GitHub issue

> The performance gain comes from **two independent axes**, each of which earns
> its own API:
>
> - **+98% RPS/core from bypassing `SslStream`** (02→03). Cross-platform, doesn't
>   require fd-binding. `TlsDetachedSession`.
> - **+256% RPS/core from binding TLS directly to the socket fd** (04 vs 05).
>   Linux-only (`SSL_set_fd`). `TlsSocketBoundSession`.
>
> The threading-model change alone (ThreadPool → epoll workers) does **not**
> account for the win (03→05: +3% RPS / −1% RPS/core). It only matters once
> combined with fd-binding, and even then it's an implementation detail Kestrel
> drives internally — not a proposed public API.
>
> `TryAccept`/`accept4` and `TCP_DEFER_ACCEPT` did **not** show measurable perf
> deltas at this load. We're dropping them from the perf justification and will
> only argue for them on ergonomics / DoS-hardening grounds if the area owners
> want to scope them in separately.

## Methodology notes

- wrk is closed-loop, 64 threads × 500 connections, 10 s sample + 5 s warm-up.
- All containers run on `cpuset: 0-3` to make per-core math meaningful.
- mem-BIO experiment (05) drops ~26 K read errors at wrk's reported `read_err`
  count — production mem-BIO would need a full `EPOLLOUT` resume state machine
  that the test rig elides. Its true RPS/core is therefore an **upper bound**.
- Single-host wrk caps total connection rate around 8–10 K/s in this WSL setup;
  bigger deltas would need either a remote load generator or a multi-host setup.
