## Reading the results

- **The threading model alone doesn't earn its keep.** 03 → 05 shows that swapping `Task.Run` for dedicated epoll workers, while staying on mem-BIO, gains essentially zero RPS/core. So if maintainers ask "can we just give Kestrel better threading and skip the TLS API?", the answer is no — the threading model only pays off in combination with fd-binding.

- **SSL_set_fd is the variable that pays off.** Going from 03 (mem-BIO + ThreadPool, 621 RPS/core) to 04 (SSL_set_fd + epoll workers, 2167 RPS/core) is a **3.5x** improvement. Almost all of that gap is the TLS-to-socket coupling, not the threading model (as proven by 03 → 05 above).

- **`SslStream` itself costs ~half the throughput per core** (02 vs 03). A targeted SslStream improvement could close part of the 02 → 03 gap, but cannot close the 03 → 04 gap (which requires fd-binding).

- **mem-BIO under load drops connections.** Exp 05 gets ~26K wrk read errors because under contention the app-layer drain hits `EAGAIN` and we surrender. SSL_set_fd in exp 04 gets 0 drops because OpenSSL's internal drain stays tighter to the socket. A production mem-BIO impl would need a full EPOLLOUT resume state machine (more code, more per-conn state) to recover these — making mem-BIO both slower AND more complex than SSL_set_fd.

## What this means for the proposal

- The **`TlsSocketBoundSession`** (SSL_set_fd) API earns its keep on per-core efficiency under high concurrency. **+148% RPS, +253% RPS/core** vs same-arch mem-BIO.
- The **`TlsDetachedSession`** (mem-BIO) API is still worth keeping for portability (Windows/Schannel, macOS/Network.framework), but it should not be sold as a perf win — it's a portability fallback. Its perf is similar to what we can squeeze out of `SslStream` with targeted improvements (~2x).
- Threading-model APIs (epoll workers, EPOLLEXCLUSIVE) without fd-binding gain nothing on their own. They're additive only.
